keyTerms:
  - term: "Formal grammar"
    definition: "A precise, mathematical set of production rules defining which strings of symbols are valid in a language — used to define a programming language's syntax."
  - term: "State machine (finite automaton)"
    definition: "An abstract model of computation made of a finite set of states and transitions between them, triggered by input — used to model parsing and lexical analysis."
  - term: "Chomsky hierarchy"
    definition: "A containment hierarchy classifying formal grammars (regular, context-free, context-sensitive, recursively enumerable) by the expressive power needed to generate them."
  - term: "Lexical analysis (tokenising)"
    definition: "The first stage of compilation: converting raw source text into a stream of meaningful tokens (keywords, identifiers, symbols)."
  - term: "Parsing"
    definition: "Analysing a stream of tokens against a language's grammar to build a structured representation (e.g. a parse tree) of the program."

indepth:
  - heading: "What a compiler is actually doing"
    body: >
      When you write code, you're writing for humans to read as much as for
      the machine to run — it's full of words, indentation, and comments
      that mean nothing to a processor. A compiler's job is to bridge that
      gap: translate readable source text into the far more rigid
      instructions a machine can actually execute. That translation doesn't
      happen in one step — it happens in phases, each one turning the
      program into a more structured, more machine-ready form than the
      last, starting with lexical analysis and parsing (the "front end")
      before moving on to semantic analysis, optimisation, and finally code
      generation.
  - heading: "Lexical analysis: turning text into tokens"
    body: >
      The first phase, lexical analysis (often called "lexing" or
      "scanning"), reads the source code character by character and groups
      those characters into meaningful chunks called tokens. Given the text
      "2 + 3", a human instantly sees a number, a plus sign, and another
      number — a lexer has to work that out explicitly, walking through
      each character, ignoring irrelevant whitespace, and producing a
      stream of tokens like NUMBER(2), PLUS, NUMBER(3). It also quietly
      strips out anything the machine doesn't need, like comments, and
      flags anything it doesn't recognise as an error at this early stage,
      before the program gets any further.
  - heading: "Parsing: turning tokens into structure"
    body: >
      Once the source has been broken into tokens, the parser's job is to
      check whether those tokens are arranged in a way that's actually
      valid according to the language's grammar, and to build a structured
      tree (a parse tree) representing that arrangement. Where a lexer only
      cares about individual words, a parser cares about how those words
      fit together into valid sentences — the same distinction as knowing
      individual English words versus knowing whether a sentence built from
      them is actually grammatical. This structured tree is what later
      compiler phases — checking types, optimising the code, and finally
      generating machine instructions — actually operate on.
  - heading: "Formal grammars and state machines — the theory underneath"
    body: >
      Both phases lean on ideas from formal language theory. A formal
      grammar is a precise, mathematical set of rules defining which
      sequences of symbols count as valid in a language — it's what a
      parser is checking input against. A state machine (or finite
      automaton) is a simple model of computation with a fixed set of
      states and rules for moving between them based on what's read next —
      lexers are commonly built as state machines, since recognising a
      token is really just tracking which "state" of partial-match you're
      currently in as you read each character. The Chomsky hierarchy
      classifies grammars by how much computational power is needed to
      recognise them, and explains why lexers (built on simpler "regular"
      grammars) and parsers (built on more powerful "context-free"
      grammars) are split into two separate phases rather than done in one.
