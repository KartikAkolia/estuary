  - term: "Functional programming"
    definition: "A paradigm that treats computation as the evaluation of pure functions, avoiding shared mutable state and side effects."
  - term: "Higher-order function"

indepth:
  - heading: "What's a programming paradigm, really?"
    body: >
      A paradigm is just a style of writing code — a different set of habits
      for telling a computer what you want. Most languages don't force you
      into one style; they let you mix and match, which is why the same
      language (Python, Java, JavaScript) can show up in more than one
      paradigm category. At the very top, paradigms split into two broad
      camps: imperative ("tell the computer exactly how, step by step") and
      declarative ("tell the computer what result you want, and let it work
      out how"). Everything else below is a flavour of one of those two.
  - heading: "Imperative programming: step-by-step instructions"
    body: >
      Imperative code reads like a recipe — do this, then this, then check
      this, then do that. It's built from variables that store values, loops
      that repeat steps, and if/else statements that branch depending on a
      condition. Two useful sub-styles sit under this umbrella. Procedural
      programming organises the recipe into reusable chunks called functions
      or procedures, so you're not rewriting the same steps everywhere.
      Object-oriented programming (OOP) goes further and bundles data
      together with the functions that act on it into "objects" — think of
      a class as a blueprint for a house, and each object as one actual
      house built from that blueprint, each with its own front door key
      (its own data) but built the same way.
  - heading: "Declarative programming: describing the result you want"
    body: >
      Declarative code doesn't spell out the steps — it describes the goal
      and leaves the "how" to whatever's running the code underneath. A
      common comparison: imperative is giving someone turn-by-turn driving
      directions, while declarative is just naming the destination and
      letting a GPS work out the route. Functional programming is the main
      declarative style you'll meet early on — it treats a program as a
      pipeline of functions transforming data, deliberately avoiding
      changing shared state so the same input always gives the same output.
      This is also where recursion (a function calling itself on a smaller
      version of the same problem) and higher-order functions (functions
      that take or return other functions) come from — both let you
      describe a repeated process without writing an explicit loop.
  - heading: "Why learn more than one paradigm at once?"
    body: >
      This module deliberately teaches paradigms side by side rather than
      one language end to end, because the actual transferable skill is
      recognising which style fits a given problem — not memorising one
      language's syntax. OOP tends to suit problems that map naturally onto
      real-world "things" (a bank account, a game character); functional
      style tends to suit problems that are really about transforming data
      in a predictable, testable way. Most working developers end up
      blending both rather than picking a side permanently, and that's
      exactly the habit this module is building early.
