indepth:
  - heading: "Data structures: the right container for the job"
    body: >
      A data structure is just a way of arranging data in memory so certain
      operations on it are fast. An array keeps everything in a single
      contiguous block, so jumping straight to any position by its index is
      instant — but inserting something in the middle means shuffling
      everything after it along. A linked list instead chains items
      together, each one pointing to the next, so inserting in the middle
      is cheap — but you can't jump straight to position 500, you have to
      walk there one link at a time. A stack only ever lets you add or
      remove from one end (last in, first out — like a stack of plates); a
      queue only lets you add at the back and remove from the front (first
      in, first out — like a checkout queue). A hash table trades a bit of
      memory for speed: it uses a hash function to work out roughly where
      an item should live, so looking something up by its key is close to
      instant on average, no matter how big the collection gets.
  - heading: "What Big-O actually measures"
    body: >
      Big-O notation doesn't measure literal seconds — a fast computer and
      a slow one would give different real-world timings for the same
      algorithm. What it measures is how the number of steps an algorithm
      takes grows as the input gets bigger, so you can compare two
      approaches independently of the hardware running them. O(1) means the
      number of steps stays constant no matter how much data there is —
      looking something up directly by its array index, for example.
      O(log n) means the work needed barely grows even as the data gets
      much bigger, because each step throws away half the remaining
      possibilities — binary search on a sorted list is the classic
      example. O(n) means the work grows in direct proportion to the input
      — checking every item in a list once. O(n²) means the work grows
      with the square of the input — common in algorithms that compare
      every item against every other item, and the reason a technique that
      works fine on 100 items can crawl on 100,000.
  - heading: "Why this matters before you've written a line of it"
    body: >
      The practical point of learning this early isn't to memorise formulas
      — it's to build the instinct to ask "how will this behave if the
      input got 100x bigger?" before committing to an approach. Choosing an
      array versus a linked list, or a simple loop versus a hash table
      lookup, can be the difference between code that stays fast as data
      grows and code that quietly gets slower and slower until it's the
      bottleneck in the whole system. That's also the "employability" angle
      Greenwich's own module description highlights — this is one of the
      most consistently tested skills in technical coding interviews.
